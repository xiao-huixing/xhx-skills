# Java 数据访问与事务代码规范

## 1. 持久化职责

- Controller 不直接访问数据库；Service 通过 DAO / Mapper 或项目已有框架持久化能力完成用例。
- DAO 方法表达查询或写入意图，返回数据、明确投影或影响行数，不决定业务流程和用户提示。
- 不为通用 CRUD 再创建只做转发的持久化包装；复杂 SQL 和数据库细节集中于相应数据访问实现。
- 类、Mapper 接口、每个方法都写功能 Javadoc，说明查询范围、返回含义或写入条件；复杂持久化过程逐步写功能注释。

## 2. 查询与写入条件

- 值使用参数化绑定，禁止拼接不可信值。表名、列名、排序方向和操作符由服务端映射或白名单选择，不能用值占位符代替标识符。
- 查询、更新和删除落实可信租户及数据范围；客户端不得提供可直接执行的权限 SQL 片段。
- 更新和删除必须有明确作用域，批量参数检查非空、去重与数量上限。
- 只查询所需字段；列表有分页、上限或明确的小数据集边界。
- Entity 转换或空页处理不得丢失 total、游标等分页元数据。
- 依照访问方式编写稳定排序、批量查询和必要索引条件，避免 N+1、无界加载和无必要的索引列函数运算。

## 3. CRUD 与一致性

- 新增与修改分别表达语义；仅在业务明确允许合并创建和更新时才使用 upsert / saveOrUpdate。
- 创建标识、租户和审计字段由服务端或已有填充机制产生，不能直接采用接口对象中同名字段。
- 修改只作用于允许字段，明确 null 代表不修改还是清空。
- 唯一性由数据库唯一约束等原子机制兜底，业务预查询只用于提前给出提示。
- 存在并发覆盖或状态竞争时，使用版本、预期状态、条件更新或必要的锁，并检查影响行数。
- 影响行数的含义由业务契约解释，区分不存在、冲突、无变化和已达到目标状态；不把所有零行一律视为成功或同一种错误。
- 逻辑删除、隐藏、停用、取消和物理删除分别表达，关联数据按业务规则处理。

## 4. 事务单元

- 多项数据变更需要共同成功时，由 Service / 应用服务公开业务方法确定事务单元；主子表更新和必须共同成立的审计包含在该单元内。
- 单条 SQL 的原子操作不为形式再拆事务服务。普通读取默认无需事务，需要一致性读取时可使用只读事务。
- 事务范围尽量短，明确回滚条件；不可控 RPC、HTTP、文件上传等不混入本地长事务。
- 未定制回滚规则时，Spring 声明式事务默认对 RuntimeException / Error 回滚，受检异常不自动回滚；按业务失败契约及项目实际配置明确 rollbackFor 等规则。
- 返回 false 或普通失败对象（如 Result.fail）本身不触发声明式回滚。写入后需要整体失败时，应让适用异常跨越事务边界，或按已有机制明确标记回滚；不能吞掉异常后正常返回而意外提交部分结果。
- readOnly 是事务子系统的提示，不是禁止写入或权限校验的保护机制。
- 本地事务不能回滚远程成功结果；跨边界流程必须在代码中表达失败处理，按真实需要使用已有回执、补偿或可靠事件能力。
- 抽私有方法不新增事务边界；不同事务边界必须通过实际生效的代理或事务机制表达，不依赖同类自调用注解。
- 多资源加锁顺序一致；业务变更、状态与成功回执需要一致时共同保存，失败不能留下半完成的成功标记。
- 批处理按业务原子性选择整批或分批，代码中明确部分成功语义，避免无限制大事务。

## 5. 数据类型与结构

- 表字段命名、标准字段、软删和版本机制遵循项目已有约定。
- 金额使用 DECIMAL / NUMERIC 对应 BigDecimal；时间类型与时区明确。
- 使用约束保护必要的唯一性、非空和引用关系；对外错误转换为业务含义，不透传数据库消息。
- 注解、拦截器和自定义 SQL 各有适用范围，不能仅凭模型存在 @Version / @TableLogic 就假定所有自定义写入都自动受保护。

回滚与只读语义参考 [Spring Transactional](https://docs.spring.io/spring-framework/docs/6.1.6/javadoc-api/org/springframework/transaction/annotation/Transactional.html)。
