# Java 异常、提示与日志代码规范

## 1. 异常与错误码

- 复用项目异常类型、错误码和统一异常处理器，区分参数、认证、授权、不存在、冲突、限流、外部依赖及系统错误。
- 只有既有异常和错误码无法表达，且需要独立处理语义时才新增异常类型；不为每个业务对象创建同构异常。
- 错误码稳定表达业务原因；HTTP 状态表达协议结果，二者不混用，也不直接以异常类名或数据库错误码作为业务契约。
- 能在当前边界恢复或转换时才捕获，优先捕获实际能够处理的具体异常；统一响应或故障隔离边界确需兜底时可以捕获 Exception，但不得将失败继续作为成功处理。重新包装异常保留原始 cause。
- 可直接向上交由已有异常边界处理的异常，保持传播；不为“保险”在每层添加 try/catch，也不捕获后仅重复记录日志或原样抛出。必要的资源释放和上下文恢复使用 try-with-resources、finally 或已有作用域机制。
- 未知错误返回安全提示，服务端保留真实异常及定位上下文；不得直接向调用方返回 e.getMessage()、SQL 或第三方原始错误。
- 禁止空 catch、吞异常、仅记录消息后假装成功、通过返回 null 掩盖系统故障。
- 中断与取消按 `06-integration-and-concurrency.md` 的控制语义传播，不能在兜底捕获中吞掉或当作普通可重试失败。
- 统一处理器负责响应形状、错误码、提示和 traceId，不在 Controller 复制异常转换逻辑。

## 2. 按接口受众选择提示

- C 端：使用安全、稳定且可理解的提示，不暴露技术异常原因；业务结果可说明允许的下一步动作。
- 业务配置端：使用领域术语说明失败对象、业务原因和可执行建议，不暴露实现细节。
- 开发配置端：可以使用配置、节点、接口等技术术语，但密钥、完整 SQL、堆栈和基础设施细节仍只保留在受控日志。
- 受众按项目模块、路由或既有元数据确定，不为每个业务方法增加临时端类型判断，也不强制新建受众框架。

## 3. 接口日志、业务日志与审计

- 通过已有 Filter、Interceptor、AOP 等统一记录接口路径、身份摘要、耗时、HTTP 状态、业务码和 traceId。
- 入参、出参优先记录筛选后的业务标识、数量和状态摘要；确需正文时先脱敏和截断。记录输入输出不等于序列化完整对象。
- 成功与否依据实际业务结果，不仅依据是否抛异常；Result.fail 等返回也应反映为业务失败。
- 业务日志说明关键状态变化；审计记录操作者、对象、动作和结果。必须与业务变更共同成立的审计在同一业务事务内保存。
- 技术日志写入失败按统一组件的失败策略处理，不在 finally 中意外覆盖原业务结果或原异常；强一致业务审计的失败语义单独明确。

## 4. 脱敏与边界

- 禁止输出密码、API key、Token、JWT、Authorization、Cookie、Session 凭据、私钥和验证码。
- 手机号、邮箱、证件号、银行卡号、地址等按已有规则脱敏；模型 toString() 也不得泄露敏感字段。
- 文件、二进制、Base64、大文本、动态表单、超大集合和流式内容只记录必要元数据，不直接写入正文。
- 请求和响应日志有长度上限；规范化换行和控制字符，避免不可信内容伪造日志。

## 5. 级别与注释

- 使用 SLF4J 参数化日志；ERROR 用于系统故障、数据不一致等，预期业务拒绝按业务含义选择级别，不把所有拒绝都当作系统错误。
- 同一异常在最能说明上下文的边界记录一次完整堆栈，避免多层重复记录。
- 日志通过 traceId 与必要业务标识关联，不将凭证作为定位信息。
- 异常处理类、日志类及每个显式声明的方法必须有功能 Javadoc；复杂分类、脱敏和审计流程每一步代码前写功能注释，执行 `01-core.md`。
