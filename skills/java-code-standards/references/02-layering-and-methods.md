# Java 架构、分层与复杂逻辑规范

## 1. 默认分层与职责

普通业务默认采用 `Controller → Service → DAO / Mapper`。ApplicationService、Domain、Repository、Adapter、Assembler 是可选职责角色，不要求每个业务建立完整层次。

| 层 | 职责与具体做法 | 边界 |
|---|---|---|
| Controller / 协议入口 | 绑定参数、执行结构校验、获取可信身份上下文、调用一个清楚的用例、包装响应 | 不直接访问数据库，不承载业务状态规则、事务或复杂跨系统编排 |
| Service / 应用服务 | 校验资源与操作权限、执行业务规则、控制状态、组织持久化、确定事务边界、组装业务结果 | 不操作 HTTP 响应，不把客户端身份当作可信上下文 |
| DAO / Mapper | 参数化查询、条件写入、落实数据范围、返回数据或影响行数 | 不决定业务流程，不返回 Result，不生成面向用户的提示 |

- 应用 Service 可以返回表达业务结果的纯数据 VO；核心规则不依赖页面组件、HTTP 行为或展示细节。
- DAO 返回 Entity 或明确的查询投影；投影与已有纯数据 VO 语义一致且项目允许时可复用，不为后缀制造相同数据的中转类。
- 已有 Mapper 或框架通用持久化能力足够时直接复用，不额外套只有转发作用的 Repository。
- Service 判断业务含义，DAO 落实查询和更新条件；DAO 返回影响行数，由 Service 解释不存在、冲突或已达到目标状态等结果。

## 2. 校验与对象边界

- Controller 校验必填、格式、长度、数值范围、集合大小和结构合法性。
- HTTP、RPC、消息、任务等不同入口各自保证输入契约，复用已有校验能力；已经在该边界验证且未经改变的输入事实，Service、DAO 和内部 helper 不再重复判空、判格式。
- Service 校验资源存在、权限、状态、额度、关联关系等业务不变量；HTTP、Feign、任务等入口共享同一业务规则。
- 数据库约束与条件更新负责持久化层的一致性，不能只依赖“先查再写”。
- 类型正确不代表权限或动态状态正确；新取得的外部数据在对应边界校验，可能变化的业务事实在实际操作点按需复核。对订单标识判非空、核对订单归属和按预期状态更新，分别承担不同职责，不属于重复校验。
- 简单字段转换使用构造器或当前类方法；复杂或重复映射再集中为转换组件。映射过程不隐藏数据访问或业务变化。
- 创建 Context / Command / DTO 必须有不同语义或边界需求；参数已经清楚时不机械增加中间对象。

## 3. 复杂逻辑的判定

满足以下任意一项，应整理流程骨架并下沉实现细节：

1. 至少三个独立业务阶段，其中至少两个阶段各有判断、循环或复杂转换，并与主流程交织。
2. 不同分支分别执行不同的校验、状态变化和保存流程，形成多条独立业务路径。
3. 本地写入、外部调用等操作具有不同失败、回滚或补偿处理，混杂在同一方法中。

业务阶段指资格校验、规则计算、状态迁移、关联处理等独立工作；参数判空、一次查询、包装返回值不分别算一个业务阶段。

方法超过 50 行、嵌套超过 4 层只触发职责检查。普通“校验 → 查询 → 保存 → 返回”、平铺卫语句、简单映射能在一个方法中清晰表达时保持完整。单一复杂算法可整体提取，不人为拆成多个业务阶段。

## 4. 流程骨架与逐步功能注释

- 复杂用例的入口方法按真实顺序展示业务阶段，细节放入有业务含义的子方法。
- 每一步对应代码前必须有中文功能注释，说明做什么以及产生的业务结果或限制；方法头注释不能代替步骤旁的注释。
- 关键拒绝分支、重放返回、循环处理、回滚和补偿步骤同样必须解释其功能。
- 注释、方法名和实际逻辑保持一致，例如“核对可交接人员”“保存发布状态”“重放原成功回执”。
- 主方法保持同一抽象层级，不夹入 SQL、JSON 解析、缓存 Key 拼接或字段逐个拷贝。
- 子方法输入输出明确，优先通过返回值传递结果；不依赖隐蔽的共享可变状态。
- 抽方法不改变原事务边界；需要真正不同的事务边界时，再使用合适的事务服务或项目已有机制。
- 所有类、方法及子方法都遵守 `01-core.md` 的功能 Javadoc 要求。

## 5. 拆方法、拆类、接口和模块的边界

| 动作 | 判定条件 | 默认做法 |
|---|---|---|
| 拆方法 | 同一职责内有完整、可命名步骤，细节打断主流程，或当前类有相同规则重复 | 先使用当前类 private 方法，保留业务顺序 |
| 拆类 | 能清楚说明独立职责，且有独立复杂规则、不同事务/依赖边界或多个类实际复用 | 拆成职责明确的具体类；只有一个调用方也可以合理 |
| 增加接口 | 存在公开契约、实际替换需求、多个实现或明确扩展点 | 只公开稳定能力，不为每个内部类自动配接口和 Impl |
| 拆模块 | 一组代码有稳定对外契约，并存在独立引用或依赖隔离需要 | 先确定代码归属与单向依赖，不按文件数拆 |

单次使用且简单连贯的逻辑就近内联；单次使用的复杂步骤打断主流程，或存在真实独立边界时，仍可按上表拆分。方法长不直接意味着拆类；类多不直接意味着拆模块。避免单纯为了降低行数、给调用改名或预留假想扩展而包装。

## 6. 业务归属与依赖方向

- 按业务组织代码，业务内部再分技术层；一个业务的数据修改由该业务公开能力负责。
- 跨业务写操作调用对方 Service 或发布契约，不直接操作对方 Mapper、表或内部实现。
- 跨业务聚合查询放在职责明确的查询能力中，避免在 Controller 散落 SQL 和拼装流程。
- API 契约不反向依赖实现模块；基础组件不反向依赖具体业务 Service、Mapper 或状态。
- 契约模块之间因真实共享需要可以单向引用，归属与方向遵循项目规则，禁止循环依赖。
- 同一业务内部的共用逻辑仍可留在业务内部；跨业务稳定技术能力才考虑公共组件，不按“多处调用”一律移入 common。
- 只有结构相似、业务含义不同的实现不强行共用。
- 循环依赖通过明确归属、上层编排或实际共享能力解决，不通过 @Lazy、静态取 Bean 或允许循环引用掩盖。
- 第三方模型和协议在实际接入边界转换；已有接口足够时不再增加无功能适配层。

## 7. 状态与分支

- 状态变更明确前置状态与允许动作，通过业务规则和条件更新共同表达。
- 简单稳定分支直接使用 if / switch；存在独立复杂规则或实际多实现时再引入策略。
- switch 覆盖允许的业务情况；未知状态按契约明确处理，不能默认走成功路径。已穷举的枚举不为形式添加空 default；旧式 switch 有意贯穿执行时，在对应代码处说明功能与后续去向。
- 不用布尔参数选择完全不同的业务流程；分别命名实际业务动作。
- 不把异常当作普通分支，不把系统故障伪装成业务成功。
- 是否建立独立 ApplicationService、Domain 或事务服务，以真实编排、规则、事务职责为依据。

## 8. Spring 代理与框架生效条件

- 采用代理模式的事务、异步或缓存等能力，必须通过其实际生效的受管调用路径使用；直接 new 的普通对象或未经过代理的同类调用，不因方法上存在注解就获得增强。
- 方法可见性与 final 等限制按具体注解、代理方式及框架版本判断，不以全部改成 public 或 final 代替边界设计。确需独立代理或事务执行边界时，复用已有能力或按真实职责拆分受管组件。
- 事务失败与回滚见 `05-database-and-transaction.md`；异步结果、异常和取消见 `06-integration-and-concurrency.md`。

代理调用边界参考 [Spring EnableAsync](https://docs.spring.io/spring-framework/docs/6.1.6/javadoc-api/org/springframework/scheduling/annotation/EnableAsync.html)；具体机制以项目配置和版本为准。
