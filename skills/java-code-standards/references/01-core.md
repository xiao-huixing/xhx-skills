# Java 核心代码规范

## 1. 基本原则与设计尺度

- 优先理解业务含义、复用项目已有能力，修改范围与用户要求对应。
- 使用满足当前需求的最少层次和对象；新增抽象必须能说明实际职责、依赖边界或复用关系。
- 同一业务概念保持一致术语；同样形状但含义不同的数据不强行合并。
- 默认中文注释，技术术语、类名、方法名保持准确英文；代码和注释不使用 emoji。
- 修正问题的权威实现，不通过绕过判断、吞异常或重复补丁掩盖问题。

## 2. 命名与类型

- 类与接口使用 UpperCamelCase，方法与字段使用 lowerCamelCase，常量使用 UPPER_SNAKE_CASE。
- 名称表达业务对象和动作。避免缺乏上下文的 `data`、`obj`、`temp`、`handle`、`process`；协议既有字段及含义明确的完整业务名称不因包含这些词而机械改名。
- Query、VO 使用有业务含义的 `XxxQuery`、`XxxVO`，不强制追加 Create、Update、List、Detail 等操作词；复用边界见 `03-web-api.md`。
- 布尔字段表达可判断的事实，如 `enabled`、`expired`；业务状态使用枚举或稳定业务编码，禁止持久化枚举 ordinal。
- 金额使用 BigDecimal 并明确精度、舍入方式；时间明确语义和时区；同一标识在同一边界内保持一致类型。
- 构造器注入依赖，依赖字段优先 final；不为只含简单规则的类机械创建接口和 Impl。

## 3. 对象与集合

- 不修改调用方传入或可能共享的 Query、集合和上下文；需要变化时创建新对象或副本。
- 简单数据模型可用 record；集合字段仍需防御性拷贝。持久化实体可沿用框架要求的可变模型，新建且未共享的局部对象可按框架方式组装。
- Query、VO 与 Entity 保持职责分离，不通过跨职责继承获得无关字段。Entity 的公共持久化基类按项目约定使用。
- 存量 Query 若依赖基类承载数据权限，先保持可信条件的传递；不能为满足形式要求直接删除继承。
- 集合通常返回空集合；单个对象不存在时明确采用空结果、Optional 或业务异常，保持该方法契约一致。
- Optional 用于表达可能缺失的返回值，不作为常规实体字段或接口参数。
- 数据转换只做映射，不隐藏查询、远程调用或状态变更；敏感字段和不同语义字段显式映射。

## 4. 类、方法与拆分信号

- 一个类承担一个主要职责，一个方法表达一个完整动作；流程编排方法可以调用多个业务步骤。
- 方法超过 50 行、嵌套超过 4 层、参数超过 4 个或文件持续增长时，检查职责与表达是否清楚；行数和数量是信号，不是机械拆分依据。
- 优先用卫语句表达拒绝条件。多个平铺判断或简单集合映射不自动构成复杂流程。
- 完整的复杂度判定、拆方法、拆类和模块边界见 `02-layering-and-methods.md`。
- 不创建无意义的转发层、万能 Utils、参数袋或为了改名而存在的包装方法。

## 5. 所有类和方法的功能注释（必须）

源码中显式声明的类型和方法，包括人工编写、AI 生成及模板生成的代码，均适用以下要求。

- 所有显式声明的类、接口、枚举、record、嵌套类型必须有中文 Javadoc，从功能角度说明负责什么、作用于什么业务对象以及职责边界；匿名实现应在创建处说明其功能。
- 所有显式声明的方法和构造器必须有中文 Javadoc，包括 public、protected、包级、private、接口声明、抽象方法、重写方法以及显式声明的 getter/setter。
- 方法注释说明：完成什么功能、输入的业务含义、返回或产生什么结果；涉及状态变化、外部影响、拒绝条件、幂等或空结果时，一并说明。
- 构造器说明装配哪些能力、用于支撑什么职责；不要只写“构造方法”。简单访问器可以用一句话说明对应字段的业务含义。
- 参数、返回值、异常存在需要解释的语义时写准确的 `@param`、`@return`、`@throws`；不填写空标签，不只重复变量名。
- 接口说明契约，实现说明实际功能和本实现的约束；`@Override` 或单独的 `{@inheritDoc}` 不能替代实现方法的功能说明。
- Lombok、record 隐式生成的方法不要求手工展开；类型与字段注释说明其含义。显式编写的访问器、构造器和重写方法仍必须注释。
- 不因一个方法短、私有或“看起来显然”省略注释；也不为了注释数量改动无关代码或生成重复的空泛描述。

## 6. 复杂流程每一步的功能注释（必须）

- 复杂流程的每一个独立业务步骤，都必须在对应代码上方紧邻写中文功能注释，说明该步骤做什么、预期结果或业务约束。
- 方法头的总说明或步骤清单，不能替代流程内部逐步注释；子方法包含多个业务阶段时，子方法内部也逐步注释。
- 关键分支、循环、提前返回、失败回滚或补偿代码，需要说明它处理的业务情形及结果；不要只写“判断”“遍历”“保存数据库”。
- 步骤注释与主方法调用保持同一业务抽象层级。只有顺序影响含义时说明顺序原因，不机械给每条赋值、getter 或语法语句编号。
- 注释必须与实际执行顺序、边界和副作用一致；代码行为改变时同步更新对应注释，不描述未实现的功能。

示例为方法片段；所调用的显式声明的方法也必须分别具备功能 Javadoc：

```java
/**
 * 发布当前租户内用户有权维护的文档，并将发布状态与审计事实共同保存。
 *
 * @param query 文档标识及用户提交的业务参数
 * @param tenantId 认证上下文中的租户标识
 * @param userId 当前发布人的用户标识
 * @return 发布后的文档业务摘要
 */
@Transactional(rollbackFor = Exception.class)
public DocumentVO publish(DocumentQuery query, Long tenantId, Long userId) {
    // 读取目标文档，拒绝不存在、跨租户或当前用户无权发布的请求。
    Document original = loadAndCheckDocument(query, tenantId, userId);

    // 核对文档允许发布的前置状态，并生成待保存的新发布状态。
    Document published = preparePublication(original);

    // 按原版本保存发布状态，发生并发修改时拒绝覆盖他人的结果。
    persistPublication(original, published);

    // 记录本次发布人及状态变化，审计失败时与发布状态一起回滚。
    appendPublicationAudit(original, published, userId);

    // 仅返回调用方需要且有权查看的发布摘要。
    return toVO(published);
}
```

## 7. 基础约束

- 常量和枚举表达业务含义；环境差异与凭证配置化，不硬编码。
- 异常、日志和安全编码分别遵循对应专题；禁止 System.out、System.err、printStackTrace 和空 catch。
- 删除失效注释、被注释掉的废代码和无功能的空分支；TODO 说明未完成的功能及原因。
- 复用已有依赖和公共组件，不为局部需求引入无实际价值的新框架。
