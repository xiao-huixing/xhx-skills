# Explain Backend Code Flow

## 目标

从当前代码还原实际运行逻辑，让用户看懂：

- 一个业务从开始到结束经历哪些步骤。
- 对外、对内以及异步入口有哪些。
- 每个接口负责什么，按什么顺序执行。
- 数据、状态和消息如何流转。
- 失败、重试、补偿和兜底如何发生。

只输出功能流程和必要的实现事实，不展开详细代码。

## 工作原则

1. 以当前代码为事实来源，文档、注释和接口描述只用于辅助确认。
2. 默认只读分析，不修改业务代码、配置、数据库或外部状态。
3. 先找入口，再沿调用链追踪，不按目录逐文件罗列。
4. 分清已确认事实、合理推断和无法确认项。不得把推断写成事实。
5. 只保留影响业务理解的类名、方法名、字段、状态和表；不贴代码片段。
6. 若代码行为与文档不一致，明确说明当前代码的实际行为。
7. 仅当范围歧义会显著改变结果时询问用户，否则按给定模块或业务继续分析。

## 分析流程

### 1. 确定范围和业务边界

- 读取仓库级指令、模块说明、路由配置和构建文件。
- 确认用户指定的模块、业务、角色、渠道和环境边界。
- 识别业务参与方，例如用户端、运营端、内部服务、第三方和定时系统。
- 找出业务起点、结束条件以及关键状态。

### 2. 盘点全部入口

检查并分类以下入口：

- HTTP、REST、GraphQL、WebSocket、CLI。
- RPC、gRPC、Feign、OpenAPI 等服务调用。
- MQ 生产者和消费者。
- 领域事件、应用事件、监听器和回调。
- 定时任务、延迟任务、补偿任务和对账任务。
- 第三方回调与本系统主动调用的外部接口。

每个入口至少记录：

- 接口类型和调用方。
- 精确的请求方法与路径，或 RPC、Topic、Event、Job 标识。
- 接口用途和所属业务阶段。
- 用户端、运营端、内部接口或支撑接口分类。

优先使用项目感知的 IDE、language server、symbol lookup、find usages 和 call hierarchy。不可用时再使用文本搜索和文件读取。

### 3. 沿调用链还原每个接口

从入口追踪到业务结果，按实际发生顺序检查：

1. 身份识别、权限校验、租户或渠道校验。
2. 参数校验、配置读取和业务前置条件。
3. 活动时间、业务状态、资格、次数、额度、库存等限制。
4. 幂等、防重、分布式锁、并发控制和风控。
5. 核心规则计算、随机选择、匹配、分配或状态判断。
6. 缓存读取与写入、数据库查询与变更。
7. 事务边界以及事务成功或回滚后的动作。
8. MQ、事件、延迟任务和异步消费者。
9. 第三方或下游服务调用。
10. 返回结果、状态码、业务状态和前端下一步动作。
11. 异常分支、重试、补偿、释放资源和人工兜底。

不要停在 Controller 或 Service 表层；追踪到关键数据落地、消息消费或外部结果为止。

### 4. 组合端到端业务流程

按业务场景分别形成时间顺序流程。每条流程应覆盖：

1. 前置准备：配置、活动、奖品、库存、资格或任务如何建立。
2. 查询或初始化：客户端如何获取展示和参与所需信息。
3. 触发入口：用户或系统如何开始业务动作。
4. 核心执行：校验、决策、扣减、分配和状态变更。
5. 结果落地：记录、资产、订单、奖励或其他结果如何保存。
6. 异步处理：消息、事件、通知和下游发放如何衔接。
7. 结果查询：客户端如何获得最终或处理中状态。
8. 失败闭环：重试、补偿、回滚、过期、对账和人工处理。

明确标注同步链路与异步链路。多个玩法、渠道或角色必须分别描述，不要混成一条流程。

### 5. 核对数据与状态流转

- 找出业务主记录、明细记录、库存、次数、额度、缓存键和消息载荷的职责。
- 说明每一步读取什么、改变什么，以及状态由谁推进。
- 还原正常状态流转和异常状态流转。
- 检查请求字段是否真正参与逻辑，返回字段是否有可靠来源。
- 检查数据库、缓存、消息和外部系统之间是否存在最终一致性过程。

只描述与流程相关的数据作用，不输出表结构、实体字段全集或 SQL 细节。

### 6. 完整性复核

交付前逐项确认：

- 所有入口都已分类，接口清单和正文一一对应。
- 每个接口都说明了用途、前置条件、执行步骤、关键分支、状态变化和结果。
- 主成功路径能从入口闭环到最终结果。
- 查询、展示、参与、发放、通知、管理和补偿链路没有断点。
- 幂等、锁、风控、次数、额度、库存和事务等关键控制已覆盖。
- MQ、事件、任务、回调、重试、补偿和对账没有遗漏。
- 已区分当前实现、未实现、疑似缺口和无法从代码确认的内容。

## 单接口说明规范

每个接口使用以下结构：

### 接口名称

- **标识**：请求方法与路径，或 RPC、Topic、Event、Job 名称。
- **调用方**：谁在什么阶段调用。
- **功能**：接口解决什么问题。
- **前置条件**：身份、状态、配置、资格等要求。
- **执行过程**：按顺序列出完整功能步骤。
- **关键分支**：成功、处理中、无资格、额度或库存不足、重复请求等。
- **状态与数据变化**：说明关键记录、缓存、消息和外部状态如何变化。
- **结果**：返回或产生什么业务结果。
- **后续衔接**：下一接口、异步消费者或客户端动作。

只写代码中存在的步骤。没有某项时明确写“当前代码未发现”，不要用通用经验补齐。

## 输出结构

按以下顺序交付：

1. **核心结论**：一句话说明业务如何完成闭环。
2. **分析范围与参与方**：说明模块边界和主要角色。
3. **公共前置流程**：配置、初始化、鉴权等共享步骤。
4. **业务流程 A、B、C**：每个场景分别列完整总体步骤。
5. **接口清单**：按用户端、运营端、内部、异步和支撑接口分类。
6. **逐接口执行过程**：使用单接口说明规范。
7. **异步、重试与补偿流程**：单独说明跨事务链路。
8. **状态流转**：列出关键状态及转换条件。
9. **当前实现注意点**：只写影响流程理解的差异、缺口和无法确认项。
10. **代码依据**：提供关键入口和核心实现的可点击本地文件链接。

流程复杂时优先使用编号步骤；接口较多时使用紧凑表格做索引，再逐个说明。只有在跨多个接口或异步节点的关系难以用文字看清时才补充流程图。

## 禁止事项

- 不贴方法实现、SQL、配置全文或大段代码。
- 不做逐行解释、类清单或目录结构复述。
- 不省略失败路径、异步链路和支撑接口。
- 不把理想设计、产品预期或注释描述当成当前实现。
- 不主动提出重构或修改方案，除非用户同时要求诊断或改进。
- 不因代码层次多而只给概括性结论；必须把功能步骤追踪完整。
